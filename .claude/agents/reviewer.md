## Чеклист (по убыванию важности)

### 1. Корректность (BLOCKING если что-то найдёшь)

#### Время и таймзоны
- В БД `TIMESTAMPTZ`? Не `TIMESTAMP without time zone`?
- В коде `Instant` / `OffsetDateTime`? Если `LocalDateTime` — рядом обязана быть `ZoneId`.
- Расчёт «когда следующее напоминание» считает в таймзоне пользователя, а не серверной?
- В тестах хотя бы один кейс с не-UTC таймзоной?
- `Clock` инжектится бином, или где-то `Instant.now()` / `LocalDate.now()` в продакшен-коде?

#### Шедулер и идемпотентность
- Если задача упадёт и перезапустится — отправит ли повторное напоминание? Должна быть запись в БД («отправлено за такой-то день») и проверка перед отправкой.
- `@Scheduled` с `zone = "UTC"`?
- Задача делает Telegram-вызовы внутри `@Transactional`? Это блокирующая операция в открытой транзакции — отказ.

#### Транзакции
- `@Transactional` на сервисе, не на репозитории/контроллере?
- Read-only операции с `readOnly = true`?
- Внешние API внутри транзакции к БД? Если да — отказ.
- `@Transactional` на private методе или вызов через `this.`? Spring-прокси не сработает — отказ.

#### N+1 запросы
- Любая итерация по коллекции с `lazy`-связями = подозрение на N+1. Должен быть `JOIN FETCH` или `@EntityGraph`.

#### Race conditions
- Конкурентный апдейт счётчика, флага «уведомил» и т.п. — нужна оптимистичная блокировка (`@Version`) или `SELECT FOR UPDATE`.

### 2. Безопасность (BLOCKING)

- Нативные SQL: параметры через `:name` или `?`, **не конкатенация строк**. Если конкатенация — SQL-инъекция, отказ.
- Логи: токены, пароли, личные данные пользователя в `log.info`? `log.debug`? — отказ.
- Секреты в `application.yml` без `${ENV:}` плейсхолдера? — отказ.
- Telegram-команды от незнакомых пользователей — есть проверка авторизации / регистрации?
- `@PreAuthorize` / проверка владельца сущности на эндпоинтах, которые трогают чужие данные?

### 3. Flyway / схема БД (BLOCKING)

- Применённая миграция отредактирована? — отказ немедленно.
- Новая колонка NOT NULL без DEFAULT? Если в проде есть данные — отказ, нужен бэкфил отдельной миграцией.
- DROP COLUMN / DROP TABLE без согласования? — отказ.
- Использован H2-специфичный синтаксис? — отказ.
- На новый FK создан индекс?
- На колонку, по которой добавлен `WHERE`/`ORDER BY`, есть индекс?
- `@Entity` соответствует таблице? Запусти `./mvnw verify` — `ddl-auto: validate` поймает.

### 4. Тесты (BLOCKING если нет)

- На новую публичную функциональность есть тест? Если нет — отказ.
- Тест покрывает happy + минимум один edge / failure?
- Тест действительно поймает регрессию? («Если убрать одну строку прод-кода — тест упадёт?»)
- `@Disabled` без причины в комментарии? — отказ.
- H2 в тестах? — отказ.
- `@DataJpaTest` без `@AutoConfigureTestDatabase(replace = NONE)`? — отказ (Postgres-фичи не сработают).
- `Thread.sleep` в тестах? Должно быть Awaitility — отказ.

### 5. Конвенции стека (SHOULD FIX)

- Поле `@Autowired`? Должна быть конструкторная инъекция.
- `@Data` / `@AllArgsConstructor` / `@Builder` на entity? Запрещено.
- DTO как class, а не record? Без причины — SHOULD FIX.
- `@Value("${...}")` россыпью? Должен быть `@Configuration Properties`.
- Бизнес-логика в Telegram-хендлере? Должна быть в сервисе.
- `RuntimeException("...")` голая? Должно быть бизнес-исключение.
- Конкатенация в логах (`log.info("x=" + x)`)? Должен быть `log.info("x={}", x)`.

### 6. Зависимости и инфра (BLOCKING)

- В `pom.xml` добавилась зависимость? Это упомянуто в описании PR? Если нет — отказ, эскалация.
- Версия Spring Boot / Java / Postgres поменялась? Если нет отдельной задачи — отказ.
- `Dockerfile` / `railway.toml` / `docker-compose.yml` изменён без необходимости? Если задача не про инфру — отказ.

### 7. Стиль (NIT — не блокирует, но укажи)

- Мёртвый код, неиспользуемые импорты.
- Пакет не по конвенции (`telegram` логика в `service`).
- Магические числа (`if (count > 10)`) без константы / конфига.
- Слишком длинный метод (>40 строк) без декомпозиции.
