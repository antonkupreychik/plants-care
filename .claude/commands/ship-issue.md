## Авто-выбор issue

Если аргумент `$1` не передан:
1. Выполни: `gh issue list --label auto-impl --state open --json number,title --limit 20`
2. Если список пуст — **СТОП**: сообщи «Нет открытых issues с лейблом auto-impl» и заверши работу.
3. Если issue **один** — используй его номер как `$1`, продолжай пайплайн ниже.
4. Если issue **несколько** — **НЕ** разводи фоновых агентов вручную (это давало неограниченный параллелизм без дозагрузки).
   Батч с ограничением параллелизма (кэп) и дозагрузкой очереди делает воркфлоу `.claude/workflows/auto-implement.mjs`:
   пул из N воркеров (по умолчанию 3), каждый тянет issue из общей очереди, доводит её этим же пайплайном до PR
   и, освободившись, берёт следующую; когда очередь пустеет — репольлит `auto-impl` и подхватывает помеченное во время прогона.
   - Запусти воркфлоу `auto-implement` (опционально `args: { cap: N }`) и **СТОП** — дальше работает он.
   - Альтернатива: из корневой оркестратор-сессии (`/Users/astonuser/plant`) — команда `/auto-run backend` (тот же кэп+backfill для обоих репо). Изнутри этого проекта `/auto-run` недоступна — это команда корня.

Если `$1` передан явно — пропусти этот блок, используй переданный номер: одиночную issue ведёт полный конвейер ниже (flyway-migrator → spring-coder → test-writer → reviewer → docs-writer).

## Предусловия (проверь сам, прежде чем начать)

1. `git status` — чисто, нет незакоммиченных изменений в текущем worktree.
2. `gh issue view $1` — issue существует, открыт, имеет acceptance criteria.
3. Если AC размыты или их нет — **СТОП**. Запусти `/plan-issue $1` сам и попроси меня утвердить план. Не пиши код «вслепую».

## Пайплайн

### 1. Подготовка
- Достань `<slug>` — короткий kebab-case из названия issue (3-5 слов).
- `git fetch origin develop && git worktree add ../plants-care-$1 -b feature/$1-<slug> origin/develop`
- Дальше работаешь в этом worktree.

### 2. Миграция БД (если нужна)
- Если задача требует изменения схемы — делегируй **flyway-migrator**.
- Жди от него отчёт: какой `V{N}__...sql` создан, риски backward-compat.
- `./mvnw verify` должно остаться зелёным после миграции.

### 3. Реализация
- Делегируй **spring-coder** с конкретным заданием:
    - Ссылка на issue ($1) и AC оттуда.
    - Что уже сделала миграция (если была).
    - Чего НЕ делать (правил из CLAUDE.md, особенно про апгрейды и Dockerfile).
- Жди отчёт: список изменённых файлов, результат `./mvnw test`.

### 4. Тесты
- Делегируй **test-writer**:
    - Какие AC он должен покрыть.
    - Минимум: happy + edge + failure. Для шедулера — обязательно идемпотентность.
    - Если задача про время — обязательно тест с не-UTC таймзоной.
- Жди отчёт: какие тестовые файлы добавлены, результат `./mvnw verify`.

### 5. Цикл fix
- Если `./mvnw verify` красное → возврат к **spring-coder** с описанием падения.
- **Максимум 3 итерации coder ↔ test-writer.** Если на третьей всё ещё красное — СТОП, эскалируй мне с описанием что пробовали.

### 6. Ревью
- Делегируй **reviewer**. Он сам прогонит `./mvnw verify` и пройдёт по чеклисту.
- Если у reviewer'а 🔴 BLOCKING → возврат к соответствующему агенту (`spring-coder` для логики, `flyway-migrator` для миграций, `test-writer` для тестов).
- **Максимум 2 итерации после ревью.** Если reviewer всё ещё блокирует — СТОП, эскалируй.

### 7. Документация
- Делегируй **docs-writer**. Он сам решит, нужны ли правки.
- Если рефакторинг без видимых изменений — docs-writer сам скажет «не требуется», это нормально.

### 8. Финал
- Финальный `./mvnw verify` — обязан быть зелёным.
- `git add -A && git commit` с осмысленным сообщением. Историю ветки не сжимай интерактивным rebase (`git rebase -i` в автономном режиме не поддерживается) — финальный PR всё равно мержится `--squash`, так что коммиты схлопнутся в один. Делай сразу осмысленные коммиты.
    - Шаблон сообщения: `<type>: <short> (#$1)\n\n<body>` где type ∈ feat/fix/refactor/docs/test/chore.
- `git push -u origin feature/$1-<slug>`.
- Тело PR положи во временный файл (например `git_pr_body_$1.md`) и передай его в `--body-file`.
- `gh pr create --base develop --title "<type>: <short> (#$1)" --body-file git_pr_body_$1.md`.
- Auto-merge включай **только если у issue есть лейбл `auto-impl`** (правило CLAUDE.md): `gh pr merge <PR> --auto --squash --delete-branch` — PR сольётся сам, когда CI позеленеет. Если лейбла нет — оставь PR на ручной мерж человеком. Если команда `--auto` упала (в репо выключен «Allow auto-merge») — не считай мерж успехом, сообщи об этом.
- В теле PR:
  ```
  Closes #$1

  ## Что сделано
  - <главное изменение 1>
  - <главное изменение 2>

  ## Миграции
  <V{N}__...sql или "нет">

  ## Backward-compat риски
  <safe / нужны два релиза / прочее>

  ## Тесты
  <какие сценарии покрыты, ссылка на тестовые файлы>

  ## Чек
  - [x] `./mvnw verify` зелёное
  - [x] reviewer прошёл (или указаны принятые SHOULD-FIX)
  ```

### 9. Отчёт мне
В чат:
- Номер созданного PR (ссылка).
- Сколько итераций было между coder/tester.
- Что reviewer нашёл (если что-то нашёл).
- Если что-то отложено — явный список с обоснованием.

## Стоп-условия (СТОП и эскалация мне)

- AC размыты — на шаге 1.
- 3 итерации coder ↔ test-writer не помогли — на шаге 5.
- 2 итерации после reviewer не помогли — на шаге 6.
- Нужна новая зависимость в `pom.xml` — на любом шаге.
- Нужно править `Dockerfile` / `railway.toml` / `docker-compose.yml`.
- Возникает архитектурный выбор, не описанный в issue.
- Issue требует апгрейда Spring Boot / Java / Postgres.

Во всех этих случаях — не «решай по своему усмотрению», а останавливайся и спрашивай меня.
